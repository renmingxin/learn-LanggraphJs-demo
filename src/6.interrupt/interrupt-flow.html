Interrupt：让图停在中间等人工确认

分析 → 暂停 → 用户输入 → 继续抓取 → 汇总。对应 6.interrupt/agent.ts

3两阶段执行：一次运行被拆成两次调用

这是理解 interrupt 最关键的一点——它不是"同一函数里同步等待"，而是"图真的结束了，下次再续上"。

阶段 A

第一次 agent.invoke()

__start__ → analyzeNode 正常执行并写入 sites；
进入 interruptNode 时抛中断信号；
invoke 立刻返回，返回的是暂停快照（report 是 undefined）；
状态被 MemorySaver 存进 thread-1。

阶段 B

进程内等待用户输入

readline 读一行：
y / yes / 是 → 继续；
其他任意内容 → 打印"已中断"并直接 return，不再调用 invoke，图永远停在检查点里。

阶段 C

第二次 agent.invoke(Command)

传 new Command({ resume: true }) + 同一个 thread_id；
interruptNode 从头重跑，interrupt() 这次直接返回 resume 值；
继续 fetchNode → modelNode → __end__，拿到 report。

4四个机制要点

机制说明
interrupt() 是抛信号 它在那一行中断整个节点，后面的代码不会执行。所以第一次运行时看不到 interruptNode 里的 console.log，这是正常的。
必须有 checkpointer compile({ checkpointer: new MemorySaver() })。没有它，interrupt 会直接报 "No checkpointer set"。
必须有 thread_id config.configurable.thread_id 是检查点的键。恢复时必须用同一个 id，否则会当作一次全新的运行。
恢复值 = interrupt 返回值 new Command({ resume: true }) 里的值会成为 const approved = interrupt(...) 的结果。想回传用户原话，就传字符串。

6四个容易踩的坑

1. 没加 approved 状态字段

节点里 return { approved }，但状态注解里没有这个 channel，恢复时会抛"无效的状态更新"。新增字段是最小修法。

2. 以为中断点之后的代码会执行

interrupt() 是抛异常，同一节点的后续语句全部跳过；恢复时整个节点从头跑，所以节点里前面若有写库、下单等副作用会执行两次。

3. 忘记复用 thread_id

第二次 invoke 若换了 id，会新建一条空线程，从 __start__ 重新跑，看起来像"中断没生效"。

4. 拒绝时仍然调用 invoke

"拒绝"的正确做法就是不再恢复，让图停在检查点；如果硬传 resume: false，图会继续往下执行，抓取和汇总照样发生。

7这套机制在生产里怎么用

审批闸门 —— 抓取/下单/发邮件这类有副作用的动作前停一下，人工确认后再执行，这正是本 demo 的形态。
人工编辑 —— interrupt 传当前草稿，resume 回传修改后的文本，节点把新版本写回状态。
多轮澄清 —— 同一个节点可以被中断多次：先问"要哪几个站点"，resume 后再问"每站抓几页"，每次靠 interrupt() 收集一个答案。
换持久化后端 —— MemorySaver 只是内存版，进程一停检查点就消失；生产换成数据库/Redis 版 checkpointer，服务重启也能续跑。
