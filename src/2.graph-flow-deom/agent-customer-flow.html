AI 客服：意图识别 + 条件路由

用户提问 → 判断意图 → 分流到不同客服节点 → 返回统一答复（对应 agent2.ts）

1一句话理解这套图

它就是一个"分诊台"：先由分类器判断问题类型，再按类型把问题交给对应的专科客服。

question
string · 输入
用户原始提问，整个图里唯一由外部传入的字段。
intent
string · 中间结果
分类器产出的标签，同时充当条件边的分支 key。
answer
string · 输出
对应节点生成的专业回复，最终随 state 一起返回。

2主流程图

紫色是分类节点，四种颜色代表四条业务分支，灰色出口是所有分支的汇合点。

分类节点 售前 售后 产品咨询 兜底

3代码与图的对应关系

图上的每一块都能在 agent2.ts 里找到对应代码。

图上的元素代码位置说明
classifyIntent classifyIntent() 让模型只输出一个标签，再用 includes 做兜底归一化
路由判断 routeByIntent 原样返回 state.intent，充当条件边的返回值
四路分支 addConditionalEdges 映射表把标签翻译成节点名，key 必须与返回值一致
四个处理节点 handlePreSale / handleAfterSale / handleProduct / handleGeneral 每个节点只改 answer，互不重叠
出口 addEdge('handleXxx', '__end__') 四条边分别指向结束，任一分支都能正常收尾

4路由映射表

条件边的映射表就是"分诊单"，左边是分类结果，右边是接诊的节点。

intent（分支 key）交给谁这个节点的人设
presale handlePreSale 热情促成，讲价格优惠，不编造活动
aftersale handleAfterSale 先安抚，再给退换货 / 物流 / 发票步骤
product handleProduct 客观专业，讲参数与选型，不确定就说以官方为准
general handleGeneral 兜底：说明服务范围，或提示转接人工

5四句话跑出四条路径

改 invoke() 里的 question，就能验证每条分支是否接通。

"你们这个套餐现在有优惠吗？我准备下单"
presale → handlePreSale
"收到的商品坏了，怎么申请退货？"
aftersale → handleAfterSale
"这款和另一款有什么区别，怎么选？"
product → handleProduct
"今天天气怎么样？"
general → handleGeneral

6三个必须记住的坑

这三个问题都不会在写完代码时立刻暴露，但会在运行时把你卡住。

1. 节点名不能等于状态字段名

状态里有 answer，就不能再注册叫 answer 的节点，compile() 会直接抛 "already being used as a state attribute"。

2. 分支 key 必须与返回值完全一致

路由函数返回 presale，映射表里也必须是 presale。写成"售前"或 preSale 都找不到分支，运行时报错。

3. 分类结果要做归一化

模型可能输出 "presale 标签" 甚至一整句解释。直接拿去当 key 会路由失败，所以代码里用 includes 匹配后再兜底成 general。

7想再加一类意图，改四处

以"投诉建议"为例，套路永远是这四步。

  1. 在 INTENTS 里加一个 key，例如 complaint: '投诉建议'，并把它写进分类提示词。
  2. 写一个处理节点 handleComplaint，返回 { answer: ... }。
  3. 在 addConditionalEdges 的映射表里加 complaint: 'handleComplaint'。
  4. 注册节点 addNode('handleComplaint', handleComplaint)，并加一条 addEdge('handleComplaint', '__end__')。
